# Label-quality flags — the side table

`src/data_prep/quality.py` writes **`data/master/label_flags.csv`** (one row per listing) and
**`data/master/label_flags_report.json`** (the counts below). Both are derived, git-ignored, and
regenerated by one command:

```powershell
python -m src.data_prep.quality --write
```

The frozen snapshot is **not touched**: `train_cohort_imputed.csv` keeps SHA256 `8c613849…` and
`train_features_full.csv` keeps `62bf8aa4…` before and after the run. That is the whole reason the
flags live beside the data instead of inside it (`CONTRIBUTING.md` §3b).

## 1. The four rules

| Flag | Predicate | Parameter | Fitted on |
|---|---|---|---|
| `deposit_suspected` | `price_vnd < threshold × median(price_vnd)` of the same `brand\|model` | 0.25, segment needs ≥30 rows, else the national median | **train only** |
| `placeholder_odometer` | `mileage_km ≤ 100` or `≥ 900,000` | — | — |
| `implausible_year` | `manufacture_year` outside `[1980, capture year]` | capture year from `scraped_at` (2026) | snapshot |
| `repeat_ad` / `is_duplicate_copy` | same `brand+model+year+mileage+price` more than once | one **canonical** row = lowest `listing_id` | identifier-only |

`flag_count` = number of the four flags set. `deposit_ratio` is kept for audit.

Two design choices worth stating:

- The canonical row is chosen by **`listing_id` alone** — no price, no target, no split. Adding rows
  later cannot re-canonicalise a group, and no validation information can decide a training weight.
- `implausible_year` is **0 in the modelling cohort** because `normalize.py` already excludes those
  records (that is what the cohort filter is for). The rule stays because the audit runs on the
  master, and because a v2 snapshot may rebuild the cohort with different rules.

## 3. Two numbers that do **not** agree with earlier documents

1. **`docs/deposit_rule_proposal.md` said 2,739 train rows (3.90%) and 566 val rows (3.78%).**
   With the rule exactly as written there (≥30-row segment, national fallback, threshold 0.25) the
   reproducible counts are **1,552 train (2.21%)** and **329 val (2.20%)**. The earlier figure is not
   reproducible from any of `train.csv` (1,783), `train_cohort.csv` (1,552) or
   `train_cohort_imputed.csv` (1,552), so it is corrected in that document rather than carried into
   any table.
2. **`tools/audit_master` prints 2,465 deposit rows and 24,575 repeated rows** on the master. This
   module reports 2,203 deposits and 30,331 rows in repeat groups over the 100,188 cohort rows. Both
   differences are explained: the audit runs on the master (100,887 rows, including the 469 rows the
   cohort excludes), and its repeat test compares **strings** (`dtype=str`) while this module compares
   the parsed numbers, so `"520000000"` and `"520000000.0"` are the same car here and two cars there.
   The side table's numeric comparison is the production rule; the audit's printout stays a diagnostic.

## 4. How the flags are allowed to be used

- **Not as features.** `tools/model_gate.FORBIDDEN` lists all eight flag columns (and `split`), so a
  feature table that carries one fails the gate.
- **As weights or filters.** `quality.cleaning_weights(flags, mode)` returns the weight per row for
  `none`, `drop_deposit`, `drop_all` and `weight_repeats` (1/k). The measured effect of each mode —
  on `val_full` **and** on a fixed `val_clean` — is in `docs/label_cleaning.md`.
